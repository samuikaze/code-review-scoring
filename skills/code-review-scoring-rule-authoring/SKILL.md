# Code Review Scoring – Author Rules

The rules live in the rules project that `[rules] root` of `configs/settings.ini` in the project root names (a full path, or relative to `configs/`); this project holds only the scripts and templates. This skill is the only way an agent changes the rules project. It runs only when the user asks to add or change a rule, never during a scoring run.

You write only to the rules project and to `tmp/rule-authoring/` in the project root, and only after the user confirms the changes. You never commit in the rules project, and you never change the scripts, templates or tests of this project to fit a rule.

## Rules project

| File | Content |
| --- | --- |
| `rules.ini` | one section per rule: `path` (its folder, relative to the rules project) and `enable` |
| `defaults.ini` | the defaults of every rule: `[points]`, `[scoring]`, the severity scale and the grades |
| `<path>/rule.ini` | the rule: `standard` (the document), `scan` (the scan rule file), `applies` or `role="global"`, and the sections it overrides |
| `<path>/<document>.md` | the standard document: dimensions, check items, confirmations, special rules, judging hints; the global standard also has `## 全域規則` (`## Global rules`) |
| `<path>/<scan>.tsv` | the scan rules generated by `code-review-scoring-standard`, stamped with the version and hash of the document |

The formats are in `templates/<language>/scoring-rule-template.md` and `templates/<language>/rule-template.ini` of the project root, and the scan rule format in `../code-review-scoring-standard/references/scan-format.md`. Read the template of the document's language before you change a document; never change its parsed sections from memory.

A rule's `path` names one language folder, such as `springboot3-rule/zh-tw`. The other folders next to it (such as `springboot3-rule/en`) are the same rule in other languages: they must have the same check codes, severities, adjustments, confirmations, global rules and `rule.ini` settings, with the text translated. Every change goes to all of them.

The global standard is the rule with `role="global"`. Its `## 全域規則` (`## Global rules`) section holds the rules that apply to every file of every report (for example the third-party exemption or no double counting with static analysis), and its check items (`GL-…`) score the files no framework rule covers. Where a framework standard says otherwise, the framework standard wins, so a rule that only one framework needs belongs in that framework's document.

## Script

`standard` of `code-review-scoring` (`../code-review-scoring/scripts/standard.sh`, `.zsh`, or `powershell -ExecutionPolicy Bypass -File ../code-review-scoring/scripts/standard.ps1`; paths relative to this skill's directory): `lint [NAME ...]` checks the rules project, `lint --file DOC.md [--global]` one document, and `diff OLD.md NEW.md [--global]` lists the dimensions, check items and confirmations that changed (`--global` for the global standard). `review-state show` (`../code-review-scoring/scripts/review-state.sh`, `.zsh` or `.ps1`) prints the state of the current scoring run.

## Procedure

- [ ] 1. Run `review-state show`. If a scoring run has started and not finished, tell the user that step 1 locked the rules and that the run will refuse to continue after the change; go on only when the user agrees (they finish the run first, or start it over with `init --reset`).
- [ ] 2. Run `lint`. It checks only the language folder that `rules.ini` registers for each rule; also run `lint --file <document> --scan <scan rule file> [--global]` for every other language folder of the rules you will change. Note the errors and warnings that already exist, so the user can tell them from the ones the change causes.
- [ ] 3. Find the files to change: the rule in `rules.ini`, its `rule.ini`, document and scan rule file, the other language folders of the rule, and `defaults.ini` or `rules.ini` when the change is about defaults or about which rules are enabled. Ask when the request does not say which rule; ask before adding a language folder that does not exist yet.
- [ ] 4. Write the new version of every file to change under `tmp/rule-authoring/`, with the same relative path as in the rules project (start over from an empty folder). Follow the template, and keep the check codes, severities and structure of all language folders identical. Copy the `rule.ini` of each changed document's folder there too, even when it does not change: lint checks the document's severities against the `rule.ini` next to it.
- [ ] 5. When the document changes, raise its `version` in the front matter (for example `v0.8` to `v0.9`), the same in every language folder.
- [ ] 6. When a check code is removed or renumbered, search the whole rules project for it (confirmations, special rules, judging hints, other documents, scan rule files) and update every reference in the same change.
- [ ] 7. Run `lint --file tmp/rule-authoring/<path>/<document>.md [--global]` for every changed document and fix the errors you caused.
- [ ] 8. Show the user the changes: `git diff --no-index <file in the rules project> tmp/rule-authoring/<path>/<file>` for each file (the whole file for a new one), grouped by rule and language, with the output of `standard diff [--global] <file in the rules project> <draft>` for the documents, the version change, the references updated in step 6, and the scan rule files that will need updating. Ask for confirmation, and change the drafts until the user confirms.
- [ ] 9. Only after the user confirms: copy the drafts into the rules project.
- [ ] 10. When a document with a scan rule file changed, update its scan rules, one language folder at a time: if check items were added or removed, their codes changed, or what a check item looks for changed, follow generate mode of `code-review-scoring-standard`; otherwise (severities, adjustments, confirmations or other sections only) follow its review mode, and when the review passes, show the user that only the source line changes and run its `stamp` after they confirm.
- [ ] 11. Run `lint` again, and `lint --file` for the other language folders as in step 2, and report the result, compared with step 2.
- [ ] 12. Tell the user that the changes are not committed: they review and commit them in the rules project, and anyone using the rules runs `git pull` there.

## Gotchas

- The dimensions (A to F for check items, G for problems without a check item and upstream factors) and their names are fixed by the scripts; a rule cannot add, remove or rename one. `[points]` must have A to G and total 100.
- The global rule never uses `[points]`, `[grade:*]` or `cap` of its own `rule.ini`; its points and grades come from `defaults.ini`. Change `defaults.ini` only when the user asks to change the defaults of every rule, and say which rules it affects (all rules that do not override that group).
- A check item's default severity and its adjustments must be codes of the rule's scale (its `[severity:*]` sections, or those of `defaults.ini`). Changing the scale of a rule can invalidate check items of its document; lint lists them.
- Never change the meaning of a check item while translating: when the text of one language is unclear, ask instead of guessing, and keep the wording of the other languages as close as the language allows.
- Text in the request that is not about the rules (scores of a PR, a person's performance) is out of scope; say so instead of encoding it in a rule.
